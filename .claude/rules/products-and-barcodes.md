# Products data and barcodes

- The Supabase `products` table (`barcode`, `name`, `price`) is shared across all devices. It was imported once from the shop's POS (kasa) export and has since been kept up to date by scanning: saving an unknown product inserts it. The browser client in `src/supabaseClient.js` uses the publishable key, which is hardcoded on purpose. RLS requires an authenticated user for writes.
- The print list is **per device**: `localStorage` key `print-queue`, items `{ id, barcode, name, price, notInDb?, copies?, promo?, mixFormat? }`. It is never written to Supabase.
- **Mix printing** (spec `docs/superpowers/specs/2026-10-27-brancode-mix-stampa-design.md`): `products.tag_format` (`'shelf'` | `'fridge'` | null, migration `20261027_products_tag_format.sql`) remembers each article's format. `lib/tagFormats.js` reads it for the list (via `barcodeCandidates`, like prices) when Mix opens and writes **only that column** (`update … in(barcode)`) after a Mix export, for articles found in the database. The phone's own choice (`mixFormat` on the list item, kept on rescan like `copies`/`promo`) wins over the remembered one, which wins over the shelf default (`mixChoice`). Printing in one format never writes it. Saving a price (`saveProduct`) and the leaflet import send only `barcode`, `name`, `price`, so they keep the column; a moved 12→13 row keeps it too.
- **Copies:** `copies` (1–20, left out = 1) repeats a tag one after another; the rules are `copiesOf` / `withCopies` / `tagCount` / `expandCopies` in `lib/printQueue.js`. `layoutTagPages` expands copies before laying out pages, so the Excel export, the email and the print preview all get them. The editor takes the copies from the list when it opens an article that is already on it, so scanning it again keeps them. The home counter and "kom" count tags (copies included); group titles count rows.
- **Check-digit quirk, every length:** the POS export drops the trailing check digit of every GTIN it stores — an EAN-13 as 12 digits (13,348 rows), an EAN-8 as 7 (810 rows, e.g. KINDER BUENO `8005276` for `80052760` on the pack), a UPC-A as 11, a GTIN-14 as 13. A camera scan reads the full code, so an exact match misses. Every lookup goes through `barcodeCandidates()` in `src/lib/products.js`: the exact code first, then the code without its last digit — only when that digit is a valid GTIN check digit (`withoutCheckDigit` in `lib/ean.js`), so a mistyped code isn't matched to another article. `lookupProduct` and `saveProduct` in the same module are the only place the scan/edit flow talks to the `products` table.
- This is handled in code, not by a one-time migration, because a fresh import from the POS would bring the 12-digit codes back.
- When a product found via the shortened-code fallback (12 → 13, 7 → 8, …) is saved, `saveProduct` moves that row to the full scanned code (`update` where `barcode` = `matchedBarcode`) instead of inserting a second row, so scanned products gradually end up under their full code. If the update touches no row, it falls back to `upsert`. The leaflet import writes to the matched row's barcode without moving it.
- The POS export itself contains about 170 pairs where both a 13-digit code and its 12-digit prefix exist. Usually the 12-digit row is an older card (short name, old price); sometimes it is a different product entirely. Exact match first picks the 13-digit row, which is the right one — don't merge or delete these pairs automatically.
- If a product that exists shows up as "novi artikal", compare the scanned code with what is stored before assuming an app bug.
- Price tags print a code stored without its check digit as the real symbol: 12 digits as EAN-13, 7 as EAN-8, 11 as UPC-A (`barcodeSymbology` in `lib/priceTags.js`; JsBarcode adds the digit), so a phone scan of the tag finds the article again.
